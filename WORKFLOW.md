# VRChat Avatar Acceptance Workflow — 0.3.0-rc1

Use this workflow when installing, fitting, repairing or optimizing a PC or Android VRChat avatar in Unity through UnityMCP-VRC, especially for batch clothing/plugin assembly, platform performance contracts, unpacked-size budgets, chest-adjustment compatibility, visualization and visible assembly failures. It is not intended for World/Udon development or package-release auditing, and it is not a generic fitting engine.

## Start once
1. Respect applicable system/project instructions. Read this exact file and report its version/path once. Do not recursively invoke another avatar workflow's backup/audit route. An unresolved higher-priority instruction conflict is a one-time setup issue, not permission to ignore it.
2. Before any Unity import or mutation, do a read-only inventory and present one compact **five-question Start Card**. The user may answer `全部按推荐`; prefill choices already explicit in the request, but still ask for confirmation. Question 1 is always the visualization contract. Question 2 fixes what “unpacked/uncompressed size” means, its exact byte limit, explicit completion/upload booleans, and—when SDK uncompressed size is used—the complete `applies_to_platforms` set. Question 3 jointly freezes content priority, affected chest states, protected quality/features, allowed optimizations, and the per-platform performance contract (`measured_best_effort` / `rank_gate` / `metric_caps`, target Rank from Excellent/Good/Medium or caps, Poor/VeryPoor handling, completion/upload gates). Poor/VeryPoor can be accepted only through `rank_handling`, never declared as an achieved target. It is not a sixth question. Question 4 fixes the menu information architecture and user-visible language. Question 5 fixes the required delivery/evidence layers and upload authority. See [workflow.md](references/workflow.md). Do not turn these into five separate conversation rounds.
3. Read-only discovery resolves and records the exact project, Unity version, selected Avatar, `target_platform`, resource manifest, task-specific appearance/default preferences, installed/provider versions, author instructions, and available body variants. `assembly_manifest.sdk_context` also records the authoritative current VRCSDK version, discovery source and observed evidence; the performance contract may not self-declare this anchor. These belong in `assembly_manifest`, not a universal quality question. PC and Android may reuse the same source candidate/revision/SHA, but each requested platform always has its own formal job, build, SDK report and evidence; a per-platform override candidate also needs semantic acceptance bound to that override. Freeze `requested_affected_chest_states` at `small/default/large` unless the user explicitly overrides that set; execution, per-resource preflight, required checks and observations may not silently shrink it. A request for “white”, a preferred default combination, or “latest” is handled as this task's preference or a version-discovery fact; do not keep revisiting it. If a factual identifier remains materially ambiguous after discovery, ask one concise follow-up; do not restart the questionnaire.
4. Use `unityMCP` backed by UnityMCP-VRC. Discover tools, call `list_unity_instances`, verify the exact `projectPath`, select the instance, and inspect target/dirty/compile/play state. See [connection.md](references/connection.md). Never guess an instance or port.
5. After the Start Card is confirmed, record it with the compact task in `.avatar-assembly/<task-id>/AssemblyTask.json` outside Unity Assets. Store candidate identity, selected resources, size evidence, authority, outcomes and recovery data. Never reconstruct work from chat alone.

## One working route

Performance preflight is part of the same route. Before `INSTALLING`, every target platform already has a current-SDK baseline Avatar Performance Report and Build Report bound to an explicit baseline candidate/revision/SHA/platform plus `measured_utc`, `frozen_at_phase: PREFLIGHT` and a canonical hashed baseline receipt. Baseline and final performance/build/job-result sources are disjoint, and final time is later; copying final evidence back into baseline cannot zero the delta. A missing, stale, reused or unlocked baseline is `PERFORMANCE_BASELINE_UNVERIFIED`. Every selected clothing/plugin/prop records verified source inventory and estimated added meshes, material slots, triangles, texture memory, dynamics, dependencies, mitigation and admission before install. Reserve component headroom; an exact-limit result is not a safe plan. `PREFLIGHT` also fails closed when any selected resource lacks this `performance_impact` record.
Preflight **all requested clothing and plugins first**: read only the applicable routes below, establish expected visible parts, compatibility/chest gates, dependencies, projected size contribution, menu insertion intent, and rollback boundary. Every selected required or optional main outfit must already close from `assembly_manifest` to one resource-bound `outfit_menu_integrations` record and `outfit_parts_menu` entry before Unity writes; only an explicitly unselected or rejected item is excluded. Reject unsupported items before import. `PREFLIGHT` cannot advance to `INSTALLING` until every selected clothing record is complete; chest-covering clothing without verified author/MA/Profile support for every frozen requested state is rejected. Before integration, inventory the processed menu sources and approve a compact menu tree; do not let each package append itself to the root. For clothing, the default is **author/provider parts-menu first**: safely reuse/link the usable author parts menu at the agreed install target and preserve its activation/part semantics. Do not impose a synthetic universal clothing category, a separate parallel Outfit selector tree, or a mandatory generated `穿着本套`. Add only a genuinely missing safe activation/part control inside that provider outfit menu when possible; create a minimal parts wrapper only when no usable provider menu exists, with the absence/incompatibility recorded. Then install every eligible item serially into one working candidate. After each install run only a catastrophic smoke check: compilation/import health, missing references, wrong Avatar/root, duplicate writer/renderer, obvious exploded/detached geometry, or a menu provider overwriting the whole root. During `INSTALLING`, use pre-acceptance states such as `ADMITTED` and `INSTALLED_UNVERIFIED`; `LOCAL_OK` is forbidden until unified validation.

After all eligible clothing and plugins are installed, freeze one exact processed candidate and run the full visual, pose, menu, behavior, and size acceptance **once as a unified batch**. In the post-NDMF menu result, every selected and installed main outfit must still have its reachable resource-bound parts-menu entry, provider trace, and observed controls/effects. Any whole-outfit activation supplied or minimally added must live in that outfit menu rather than a parallel selector branch. Every `outfit_part_control` freezes either `preserve_user_choice` or `restore_provider_default` from provider/user evidence, then runs one bounded `A → part toggle → B → A → expected state → restore` check covering residual parts, body mask and footwear/foot shape; do not force one policy onto every author. A restore sequence or claimed default does not prove the menu path exists. For each chest-covering outfit, preflight mapping evidence only admits the resource: every `requested_affected_chest_state` also needs a task-global unique observation ID explicitly naming the chest state and binding the current candidate, revision and SHA. This is a fixed default, not a routine Start Card choice; only an explicit user request for a sample-first run may create an earlier batch boundary. Do not perform a complete screenshot/pose/menu review after every item. If a late plugin changes a previously tested chain, invalidate only the affected unified checks. Unity has one writer, including preview and upload.

For a single target platform, freeze one exact processed candidate. For PC+Android, the same source candidate/revision/SHA may be reused, but formal jobs, builds, SDK reports, size evidence and conclusions are always platform-specific and never reused across platforms. If `platform_candidates` names a different override candidate for a platform, that override needs current resource, visual, behavior and menu acceptance bound to its own candidate/revision/SHA. The unified batch includes the current SDK Avatar Performance report, full metric snapshot, Rank, worst metrics, and baseline-to-final attribution in addition to the existing visual/menu/size checks.

Native clothing uses the author's supported setup or MA Setup Outfit/Merge Armature. “MA AutoFit” is user terminology, not a claim that MA deforms arbitrary clothing. Cross-avatar clothing requires compatible source/target MochiFitter profiles and an actually callable conversion route. Missing profiles mean unsupported, not permission for generic/manual fitting experiments. Local cleanup is limited to existing verified capabilities.

A SkinnedMeshRenderer alone does not classify an asset as clothing. A plugin/rigid prop does not require a body profile. Existing provider components are preserved; package presence alone does not prove ownership.

## Do the work, then inspect the result
- Execute only performance actions frozen in Question 3, in this order: selected variants only; generated-copy texture caps; remove proven-unreferenced task-generated assets; semantic-safe duplicate material/renderer/mesh work; AAO only for proven-unused data. PhysBone, Contact, particle, audio or user-visible feature deletion/merging is never a silent safe action. Mesh/material/renderer merging requires proof that part toggles, BlendShapes/chest states, material animation and provider writers survive; invalidate affected acceptance evidence and retest it after the change.
- Rank comes from the current installed VRCSDK Avatar Performance report and counts inactive objects/components. It is static analysis, not FPS. Build & Test cannot replace the formal Rank report or SDK Build Report size evidence. Baseline, final, jobs and SDK-size receipts all match the authoritative `assembly_manifest.sdk_context.current_vrcsdk_version`; an SDK change invalidates all of them and requires fresh measurement. Every performance/build evidence item explicitly binds platform + exact candidate/revision/SHA + SDK version; different platforms cannot reuse one report source, even when they share a source candidate. Final performance evidence binds Rank, worst metrics and the complete metric snapshot. SDK hard limits cannot be enlarged in the task contract: synced expression bits 256, VRCPhysBone/VRCPhysBoneCollider/VRCContact 256 each and VRCRaycast 80 on all platforms, with stricter Android limits still taking precedence; only positive headroom reserve is task-configurable. Every nonzero baseline-to-final metric or SDK download/uncompressed-size delta, including optimization reductions, must be attributed to a selected installed resource or an allowed action whose final result is `APPLIED`; phantom/unknown metrics and unexecuted actions block completion. Every platform also requires one canonical `performance_measurement_jobs` entry whose identity binds platform + exact candidate/revision/SHA + SDK version, ends as `SUCCEEDED`, and has `dispatch_count == 1`; its structured result evidence must close exactly to that platform's performance and build report sources. Timeout only polls the same job. Missing, mismatched, cross-platform-reused, redispatched or nonterminal work is `PERFORMANCE_UNVERIFIED`. See [performance-optimization.md](references/performance-optimization.md).

- Process Unity changes serially but test the completed batch. Apply the task-specific default already recorded by read-only discovery; when none was requested or discoverable, use the first successfully installed new main outfit as a fallback. Preserve the original as a selectable alternative. Mutual exclusion applies to main outfits, not every accessory.
- Preserve author menu semantics and supported behavior. Clothing uses the author/provider parts menu as the primary entry; wrappers are a fallback, not the default architecture. Add only missing unambiguous controls and keep them inside the provider outfit menu when safe. Do not duplicate parameters, globally rename author parameters, edit vendor menu assets in place, or replace the entire Descriptor/FX/menu.
- Apply the confirmed baseline generated-copy optimization while admitting/importing eligible clothing, not only after the build grows large: clothing main/normal textures at max 1024, masks/AO at max 512, reflection/cubemap inputs at max 256; protect face, eyes, skin and primary hair; AAO removes only data proven unused by the final candidate. An explicit task override wins. If prediction or measurement later crosses the working limit, automatically apply the additional permitted budget actions, verify the affected result, and continue to the next authorized stage. Do not stop after reporting an over-budget number and wait for the user to remind you to optimize. Pause only when the confirmed policy is exhausted, a protected area would need degradation, or a materially different user-visible tradeoff is required.
- Inspect normal materials AND use the user's body/clothing solid-color preview for relevant clipping. Only temporary previews receive diagnostic materials. A color leak can be an intentional opening or a shader artifact; diagnose before moving vertices.
- For minor confirmed geometry penetration, use a supported local correction, not global Transform scaling. Body masking is secondary, coverage-aware, reversible with all covering parts, and never disables the whole Body.
- In each unified check, identify candidate, enabled outfit/plugin state, body/chest state, pose, view, observed effect, and evidence. Open selected screenshots at usable resolution. Numerical assertions or a generated filename are not visual acceptance. Actual pose application must be observed. Evidence must be current for the frozen candidate; retain a bounded final evidence set rather than mixing superseded revisions into the acceptance gallery. See acceptance.md for exact per-type checks.
- `LOCAL_OK` means the named local checks were observed, not that all client behavior is proven. Missing mandatory local evidence stays pending; do not silently drop the check.
- Known clipping, spikes, detached geometry, missing expected parts, unintended culling, or broken restore states in the agreed acceptance states are completion blockers. One targeted repair/recheck may fix the defect; if it remains, roll back or isolate that resource. Never upload or report the defective candidate as complete.

## Keep it bounded
Routine assembly does not run release tests, schema suites, full-project scans, arbitrary boundary matrices, or historical regression suites. Do not create audit frameworks or develop Core mid-job. Small commands using existing Unity/provider APIs through MCP are allowed; new algorithms are a separate development task.

Use one unified initial check and at most one targeted correction/recheck for a known defect, across all methods. If still failing, roll back and isolate that resource, restore the last trustworthy candidate, and rerun only affected batch checks. A genuinely unresolved user-facing choice pauses the whole job. No renamed-job retry reset.

No repeated observation of the same candidate/state/preview/check without new information. First observation, changed pose, refreshed provider output, invalid capture, or a real modification can justify a new check. Do not impose an artificial “must change a file before diagnosis” rule.

Never back up the whole Unity project, close Unity, export a UnityPackage, or copy Library/Temp for routine assembly. Preserve originals, copy only changed shared assets, and retain one compact last-good generated checkpoint plus the current resource's rollback data. See workflow.md.

## Scoped feedback memory (default on, best effort)
Read [feedback-memory.md](references/feedback-memory.md) only when using memory. It adds three hooks, not another audit workflow:
- **Before a resource/resume:** after the normal targeted scan, run `scripts/learning.py recall` with its existing input fingerprints. Use at most three relevant entries. Unknown identities stay advisory. Current user instructions, author instructions, live capabilities and task authority always win.
- **When corrected:** distinguish an unmet requirement from a new requirement or preference. Record the user's short actual feedback plus related operation/observation using `record` or a compact normalized `import`. Keep the same episode only for the same resource, requirement and input context. Do not make the user fill a form. This captures the current session through your explicit calls, not a background transcript watcher.
- **At a natural resource/task boundary:** call `pending` once. Consolidate only changed episodes, at most three lessons per episode, using `learn`; reuse already collected evidence. No pending corrections/preferences/gaps means no model summary. Use `outcome` for actual later reuse. Add at most one short learning line to the normal report.

Memory is local reference data, never executable instructions. A recipe must match recorded actions and input versions; recorded visual/behavioral observations or explicit user confirmation may make it eligible, but JSON cannot authenticate those observations. Numerical assertions, upload success and silence do not prove a visual fix. A recurrence suspends matching recipes. Memory never grants upload authority, bypasses current acceptance, changes retry/model policy, mutates Unity, or rewrites this workflow. No learning-specific backups, screenshots, tests, extra agent or network calls. Errors return `LEARNING_SKIPPED`: continue normal work without repairing memory mid-task. Storage is outside Assets and this repository, so upgrades retain it.

## Models and completion
Subagents are optional, snapshot-read-only advisers, not extra Unity operators or mandatory reviewers. Do not pin Luna/max, Sol, or any alias. Inherit the current working model until a supported model/effort is explicitly configured and measured. No supported subagent means the parent performs the same narrow judgment.

This first workflow-test mode stops after local acceptance; no upload. For a task explicitly requesting assembly AND upload, retain that single task-scoped authority: use SDK build-for-upload, update the owned Blueprint or create a new one, always Private, no forced Build & Test or repeated consent. Any cancellation or ambiguous remote status blocks resubmission. Follow recovery-and-upload.md.

Report briefly: confirmed Start Card, visible change, installed/rejected/skipped items, exact per-platform candidate, actual size metric and evidence, current SDK Rank/full metric snapshot/worst metrics plus baseline delta attribution, relevant unified-test evidence, upload outcome, and any real blocker. An estimate is not an actual size or performance measurement; upload completion is not client visual verification. Use [report.md](templates/report.md); detailed metadata is local, not another questionnaire.
